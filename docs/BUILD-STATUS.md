## 0.3.1-dev implementation covered by CI

- Android minimum SDK is API 24 (Android 7.0+); Windows native runner uses the Windows 10+ API baseline for Windows 10/11 x64.
- Windows settings can discover local IPv4 interfaces and classify common Wi-Fi, Ethernet and RNDIS/USB-tether interfaces. Classification is based on interface names and is best-effort.
- WebRTC includes Google and Cloudflare STUN endpoints plus optional coturn TURN REST credentials generated by the Go signaling server. The default credential lifetime is 900 seconds when TURN is configured.
- ICE candidates are batched in groups of up to 8, with a short batching delay; interrupted peer links make up to three bounded recovery attempts.
- File transfer uses ordered 60 KiB payload chunks plus a 40-byte frame header (61,480 bytes total), keeping the full message under 64 KiB. Sender backpressure uses 4 MiB / 2 MiB high/low watermarks.
- File transfer has consent, progress, cancellation and filename validation. The per-file limit remains 100 MiB. The receiver still assembles a complete file in memory before saving, and only one incoming receive/save is allowed at once.

## Still requires physical-device validation

CI proves static analysis, automated tests and native compilation. It does **not** prove that the features work across real hardware, drivers, routers or carrier networks. Validate on a physical Windows 10 PC, Windows 11 PC and Android phone:

1. Pair Windows ↔ Android on the same Wi-Fi/LAN.
2. Pair over Ethernet (PC wired to the router, phone on the same LAN).
3. Pair over Android USB tethering and confirm the correct RNDIS IPv4 address is selected.
4. Send files in both directions (small, medium and near-100 MiB); compare file size and SHA-256 hashes.
5. Test accept, reject, cancel, cancel-save-dialog and disconnect/reconnect during transfer.
6. Monitor Android RAM while receiving a large file.
7. Test remote access from a different Internet connection, first without and then with coturn.

## Current boundaries

- **No public TURN or signaling service is operated by MTUNZ.** A self-hosted Linux VPS template is provided under `deploy/`; users must supply their own host, DNS records, firewall rules and secrets. STUN alone cannot guarantee direct connectivity through carrier-grade or restrictive NAT.
- **No public service is deployed by this repository.** The `deploy/` template puts the signaling service behind Caddy HTTPS and configures coturn over UDP/TCP. Do not expose port 8787 directly to the public Internet. TURN-over-TLS is not enabled in the sample yet.
- USB support means ordinary IP networking over Android USB tethering/RNDIS or Ethernet. It is **not** a raw direct-USB transfer protocol and does not use ADB.
- The receiver's in-memory assembly makes the 100 MiB cap a conservative limit, not a guarantee of low RAM use.
- Remote keyboard injection, clipboard, audio, accounts, persistent trusted devices and iOS/iPhone are not implemented in this milestone.

## Self-hosted deployment template

- `server/Dockerfile` builds a non-root Linux signaling container.
- `deploy/compose.yaml` starts signaling, Caddy HTTPS and coturn; `deploy/.env.example` contains placeholders only.
- The workflow validates Compose configuration and builds the signaling container. This does not deploy a VPS, provision real DNS/certificates or prove external NAT traversal.
